# Curate a batch

You curate a batch: its publications, each curated by a `curator` agent from its full text, then reviewed by a `reviewer` agent, whose findings its curator fixes; you merge the results, dry-run them and report. The goal is a batch that passes the dry run. Read no publication and no doc: this skill is the whole process. No need to `cd`: the scripts run by their path from the repository root, and each path is written from `<batch>`, as in `<batch>/<pmid>/curation.txt`.

1. **Batch**: `<batch>`, the batch directory the prompt names, otherwise the oldest batch, in the oldest run of `<workdir>` (the curation's root directory), with a `pmids.txt` and no `author.txt`, written as its absolute path (`realpath`), so that the `dir` each curator is sent is right from any directory. `pmids.txt` is the batch, never changed. Check the directory against it before anything else: one publication directory `<batch>/<pmid>/`, with its `manifest.json`, per PMID, and no other. Anything else: stop and report it.

2. **Author**: write the author, which takes the batch, at once: the curators' model and effort, `echo "<model> (effort <effort>, $AI_AGENT, commit $(git rev-parse --short HEAD))" > <batch>/author.txt`: `<model>` the model ID your system prompt gives for the `model` of `curation/agents/curator.md` (`opus`: the latest Opus), `<effort>` the curators' effort, medium unless the user's message names another, `$AI_AGENT` the Claude Code running you and `git rev-parse --short HEAD` the commit of this repository, as in `claude-opus-5-5 (effort medium, claude-code_2-1-312_agent, commit 3f06368)`. It is written once, here, and stays the batch's author: the model of the session may change later, which changes nothing; never mention it, never ask about it.

3. **Curate**: one `curator` agent per publication, a few at a time, each started at the curators' effort, sent only `dir: <batch>/<pmid>`, `pmid: <pmid>`. It writes `descriptions.jsonl` and `curation.txt` in its directory. Without them, run it once more; still without them, write its note in `<batch>/<pmid>/curation.txt`: `SELECTED`, then that its curation did not finish. A curator's `SELECTED` note names the files it could not have: try to have them as any file, with the tools only (`uv run ./curation/scripts/download.py <batch>/<pmid>/work <url>...`), never the browser: the curation runs without the user, asked for the browser only at the end (below). With any of them had, resume that curator (SendMessage) to curate again with them, once per publication. A file not had leaves the publication `selected`, with its descriptions.

4. **Review**: once its curator is done, each publication with its two files is reviewed by one `reviewer` agent, started at xhigh effort, unless the user's message names another effort, sent only `dir: <batch>/<pmid>`, `pmid: <pmid>`. It replies `<pmid>: nothing wrong`, or one line per wrong thing. A suspicious reply (a part of the review skipped, a finding without its place in the publication, `nothing wrong` on a publication whose note names experiments it does not cover, a reply that misreads its task) gets one resume (SendMessage) making its task precise. Without a reply, run it once more; still without one, the publication is not reviewed. Each wrong thing found: resume the curator with the reviewer's lines, once; it fixes its files in place and replies what it fixed and what it did not, with why.

5. **Merge**: `cat <batch>/*/descriptions.jsonl > <batch>/descriptions.jsonl`, then `uv run ./curation/scripts/notes.py <batch>`, which writes `<batch>/publications.jsonl` from the publications' `curation.txt`, the state from the note's first word. The write dates the note.

6. **Dry run**: `uv run ./database/scripts/batch.py <batch>` applies and checks everything in one transaction, then rolls it back. When it refuses rows or finds errors, report them as they are; the user directs the fix (a publication's diff against its live descriptions, `uv run ./database/scripts/diff.py <pmid> <file>`, included), then dry-run again.

7. **Reply**: whether the batch passes the dry run, else its refused rows and errors; what each batch file holds, in descriptions and publications; the publications with a relevant file missing, with why; from the notes, the `best-effort` values and the supplementary files downloaded or not; the publications reviewed and how many have nothing wrong, each finding fixed or not by its curator, with its publication and why, the publications not reviewed, the reviewers resumed, with why; from the agents' replies, the tool errors; the files the browser could have, below. Never ask for the commit.

**Browser**, at the end only: when a file the tools could not have (one a `SELECTED` note names, one a finding not fixed lacks) would settle a point of the curation, the reply proposes to download it with the browser, with its publication and the point it would settle. Only on the user's yes, in a session with browser tools: the file's URL or the article's page; a closed file through the library proxy once the user has logged it in, `https://doi-org.docelec.univ-lyon1.fr/<doi>`, never credentials entered, a captcha passed by the user. The browser saves each download in its download folder (ask the user where it is when you do not know), several seconds late, sometimes as `<name> (1).<ext>`, one download per page: navigate the tab to each file's URL. Move each file at once into `<batch>/<pmid>/work/`, convert it with `uv run ./curation/scripts/parse.py <batch>/<pmid> work/<file>`, which prints its manifest entries, and resume that publication's curator with them to curate again; then merge, dry-run and reply again, with what the file settled.

**Commit**, only when the user asks for it: `uv run ./database/scripts/batch.py <batch> --author "$(cat <batch>/author.txt)" --commit` writes the new descriptions, the publication states and notes, each note after its date and the author, `author.txt` as written at the start, whatever model runs the session now (`[2026-10-29, claude-opus-5-5 (effort medium, claude-code_2-1-312_agent, commit 3f06368)] CURATED …`).
